## 3. Method

Authoritative method: [`docs/benchmark-methodology.md`](benchmark-methodology.md). The whole session is driven by `bench/m1/run-read-session.sh` in this order (ordering matters: io_tester writes 2×10 GiB setup data to the same NVMe, so it runs last); 30 s settle between phases. All cells: one fresh process, `taskset -c 2`, O_DIRECT, seed 20261113, engines interleaved by rep.

|---|---|---|---|---|
| 1 | `run-read-matrix.sh` | W1–W4 4K randread, three-way, fio `matched` | 10 s warmup + 30 s measured | R=5 |
| 2 | `run-fio-brackets.sh` | QD64: `default`, `batch8/16/32`, `sqpoll`, `libaio`; QD128: `default`, `libaio` | 10 s warmup + 30 s measured | R=3 |

| 4 | `run-perf-cells.sh` | CPU/syscall cost at QD1+QD64, three-way; fio comparator in `default` (`perf`) **and** registration-matched (`perf-matched`) configs | 10 s warmup + 40 s measured; `perf stat -p <process tree> -- sleep 30` attached at warmup+1 s (30 s steady-state window) | R=3 |
| 5 | `run-seqread-matrix.sh` | W9 (QD1), W10 (QD8), W11 (QD32), 1 MiB three-way; fio `matched` at QD1, `regfile` at QD8/32 | 10 s warmup + 30 s measured | R=5 |
| 6 | `run-iotester-check.sh` | seastar `io_tester` W1/W3 + `/dev/null` probe (W24) | 30 s measured, setup run prefills one 10 GiB shard file first | R=3 |

**Protocol notes / deviations (full list in `notes.md`):**

1. `nvme-data/` writable bind mount exists for this session (host fstab not yet persisted) — this is why io_tester and the later write block are possible.
2. `seastar_file_bench` latency sampling was fixed for this session: it now uses a uniform Algorithm R reservoir per fiber (`sampled = samples < ops` is truthful) instead of describing only the first samples of a long run. Binary SHA256 is in `manifest.txt`; only this session's seastar tails use the fixed sampler.
3. fio `matched` (`--registerfiles=1 --fixedbufs=1`) is the M1 reference; `default`, `batch8/16/32`, `sqpoll`, `libaio` are disclosed brackets (F0).
4. 1 MiB registration: `qd × 1 MiB` fixed buffers exceed `RLIMIT_MEMLOCK = 8 MiB`, so fio runs `regfile` (`--registerfiles=1` only) at QD8/32 and JUring itself falls back to unregistered arena buffers there (`io_buffer_mode` per cell). Both sides therefore drop fixed buffers; this is disclosed, not silently equalised.
5. `perf stat -p <process tree>` counts the engine process tree (fio forks its job); kernel io-wq CPU is outside the process tree and is attributed to neither engine — this can only understate seastar's CPU cost (it does not use DEFER_TASKRUN). Ops in the perf window are estimated as `IOPS × 30 s` (perf_summary.py convention, < 1.5 %).
6. No cold-cache drop (root-only); O_DIRECT cells are cache-insensitive but metadata/extents are warm. `source`/`target` device is the same NVMe for every cell.
7. One accidental pre-session io_tester block (14:08–14:11 local, harness plumbing) wrote ~20 GiB to the device before this session and was deleted rather than cited; all session cells were re-run after it and the session log records the ordering.

## 4. Device-state gating and fast-state subsets

The host/NVMe is bimodal at QD64: fast ≈ 320–325k IOPS at p99 ≈ 0.5 ms vs slow ≈ 255k at p99 ≈ 1.7 ms (baseline §6/§9.2). A fixed p99 < 600 µs rule cannot be used at QD128: during the session all three engines clustered at p99 ≈ 758–916 µs in the QD128 fast state (p99 scales ≈1.7× with QD). The gate is therefore calibrated per QD (Lead calibration):

1. **p99 criterion** (single-thread 4 KiB randread QD64/QD128): QD64 fast iff **p99 < 600 µs**; QD128 fast iff **p99 < 1200 µs** (2×).
2. **IOPS anomaly criterion** (all cells, any QD): a rep is anomalous/slow iff its IOPS is **< 0.92 × the maximum IOPS of the same (case, engine, variant) cell**. This catches the QD64 255k-vs-325k state and low-throughput transients (e.g. fio-matched W1 r2 at 88.0 % of its cell max, p99 ≈ 330 µs). Flagged, **never trimmed**.

Both are reported for every cell: **(a)** the all-reps mean ± 95 % CI is the primary statistic and always includes every rep; **(b)** the fast-state subset is reported with n and its own 95 % CI, listing the excluded rep ids and whether the two engines' classifications differ. Gates use the all-reps statistic; only when a cell is unstable (CV > 10 %, mixed state or > 10 % IOPS spread) does the gate switch to the fast-state subset (stated explicitly with its CI, §14). A subset with < 2 paired reps is INCONCLUSIVE, not a pass.

## 15. Threats to validity

1. **Single machine, single drive, single kernel** (Ryzen 9 3950X + one GIGABYTE/Phison E16 NVMe + kernel 7.0.12-201). No generalization to other drives/controllers/kernels; re-run M1 on any kernel/driver change (DEFER_TASKRUN/task_work behaviour is kernel-dependent).
2. **Device state / SLC-GC is the dominant confound for any cross-dataset comparison.** Bimodal host state is real (§4; W4 had one slow rep per engine, gate used the disclosed subset). The controlled aged-vs-fresh experiment (§11b) shows the same engine gains 5.2–5.6× at QD1 and 1.12–1.68× at QD64 on a freshly written file — so **absolute numbers are only comparable within one dataset data state**; that is why io_tester's fresh-file numbers are not comparable (§11) and why the M1 matrix is valid only because every cell uses the same aged file back-to-back. Additionally, ~20 GiB of accidental pre-session io_tester writes and 20 GiB of io_tester setup writes on the same NVMe preceded/followed the read cells (notes deviation 8).
3. **seastar is asymmetric by construction** (no ring flags, no registered files/fixed buffers, 200-entry ring, io_queue + futures, busy-poll reactor at low QD). It is a bracket, never a win/loss. Its QD1 CPU (383k cycles/op) is a runtime property, not a defect of the comparison.
4. **fio configuration dominates fio numbers**: default 290.4k vs matched 304.1k IOPS at QD64, and `sqpoll` collapses to 10.8k. Only `matched` is the reference; all brackets are disclosed. The old README's "fio default" was not a fair reference.
5. **Latency definitions differ**: JUring/seastar before-submit → completion (both uniform reservoirs after the seastar sampler fix); fio `clat`. Only W15/W16 p99 tails are gated. At 1 MiB/QD32 the p99 of ~10–15 ms is the **expected queueing tail** (Little's law mean ≈ qd/IOPS ≈ 6.8 ms at ~4.7k IOPS), not a `clat` artefact; the earlier low JUring seqread tails were a harness latency-attribution defect, repaired and re-measured (§6/§16.4). The JUring QD1 p999 (631 µs, max 7.1 ms) is a **JVM-tail** effect, i.e. L0+JVM conflation.
6. **Sandbox sharing / host load**: session preflight required governor `performance`, io_uring enabled, loadavg gate and no foreign >20 % CPU process; per-cell loadavg and device-sector deltas are in `cell-meta.tsv`. The workspace is on a different NVMe and never used for I/O.
7. **Rep count / transients**: R=5 for throughput/latency; low-throughput transients are flagged (IOPS < 0.92 × cell max) and kept, not trimmed. Gate cells use all reps except where a cell is mixed-state (W4), where the fast-state subset is used and stated. The 95 % CI half-widths are quoted in every gate row; a "parity at ±5 %" claim additionally needs the 90 % CI of the ratio inside [0.95, 1.05] — only labelled where true.
8. **JVM effects**: fresh JVM per rep, fixed flags, 10 s warmup; JVM share of per-op CPU is real and belongs in §8. `seastar_file_bench` was rebuilt with a uniform reservoir for this session (SHA in manifest) — seastar tails from earlier sessions are not comparable.
9. **No hugepages** (`HugePages_Total=0`): both engines use the THP path; a host with hugetlbfs is a different F0-disclosed configuration.
10. **Write half measured but INCONCLUSIVE (session 11, §13 + `docs/m1-write-report.md`)**: the full matrix ran under the frozen Step-A protocol; write rule 1 is INCONCLUSIVE because of device write-state cliffs (36/130 runs) and D7 instability, no write-parity claim. The six failed-init 1M fio-`matched` attempts (8 MiB memlock) are disclosed and were re-measured as `regfile` (Amendment A1). Deviations disclosed: session-once D1 preconditioning overshot to 120 GiB instead of the intended ~32 GiB (deeper steady state), rests between rep groups only, fresh write file, seastar write path first validation. The write cell-meta fio p99 is in ns and must not be cited (units defect; use cells-normalized.csv / raw JSON).
11. **Provenance imperfections (documented, not hidden)**: (a) the fio `perf` and `perf-matched` perf runs shared a filename stem, so the default run's raw JSON/txt was overwritten — its CPU numbers are computed-only rows from `perf-cells.tsv`; (b) `cell-meta.tsv` has no phase column and the perf phase reused W1/W3 ids, so 18 meta keys are ambiguous and the analyzer excludes them from the value cross-check, taking perf cells from `perf-cells.tsv`; (c) the first 5-minute session attempt was aborted and nothing from it is cited; (d) one accidental io_tester block was deleted rather than cited.
12. **perf scope**: kernel io-wq CPU is outside the process tree and attributed to neither engine; this can only understate seastar's CPU cost (it lacks DEFER_TASKRUN).
13. **JUring harness latency-slot collision (found by external review; fixed and repaired in this dataset).** The harness derived the per-op latency slot from `user_data & slotMask`, assuming the low bits are a monotonic op id — true for fixed-buffer ops (`UserData.encodeFixed(type, bufferIndex, opId)`) and NOP, but **non-fixed `READ_EXT` encodes the buffer ADDRESS** (`UserData.encode(READ_EXT, buffer.address())`) and the arena buffers are 4096-aligned, so every in-flight non-fixed read collided on one slot: a completion's timestamp was a later submission's start, understating latency. Affected exactly the 10 JUring `io_buffer_mode=arena-unregistered` cells — W10 (1 MiB QD8) and W11 (1 MiB QD32); the old p50 ~176–203 µs / p99 ~448–638 µs were physically impossible (Little's law implies 1.68/6.71 ms). Fixed by indexing the latency/buffer bookkeeping by buffer with `udOfBuf` attribution, plus a guard that warns when measured mean latency differs from `qd/IOPS` by > 25 %. Invalid originals archived outside the session dir at `bench/results/_invalid/m1-2026-11-13/latency-slot-collision/` (and the first wrong-workload repair at `.../workload-mixup-randread/`); neither is cited. The 10 cells were re-measured with `bench/m1/repair-w10-w11-latency.sh` (10 s warmup + 30 s, R=5, `seqread`, same seed/CPU). Harness source sha256 `16801adeaf80e8191254a80f1d59b131bcc41465676c8a7047140d7705750866`; the repair cells were measured with the previous fixed build `8ab28702…`, identical except the added Little's-law warning. Corrected values are in §6; **M1 verdict/gates are unchanged** (read path PASS; seqread tails are not gated — only W15/W16 — and IOPS/CPU were never affected).
