# Baseline measurements — JUring vs seastar read path (2026-11-13)

Status: **phase 1 (fio) and phase 2 (JUring) complete**. seastar is **not** measured:
it cannot be built or run in this sandbox (no cmake/ninja/liburing/boost dev packages,
the seastar tree is a read-only mount, and hugepages/root are unavailable),
so this document is a host/device baseline plus a JUring-vs-fio comparison only.
It is the "where are we now" input for `SEASTAR-PLAN.md` §2.1, not a JUring-vs-seastar result.

- Host: `treediagram`, AMD Ryzen 9 3950X (16C/32T), 62 GiB RAM, Fedora 44, kernel
  `7.0.12-201.fc44.x86_64`, date 2026-11-13.
- Data disk: GIGABYTE GP-ASM2NE6100TTTD 1 TB NVMe (Phison E16, PCIe 4.0 x4), ext4 at
  `/mnt/TestData`, **mounted read-only** (`/dev/nvme1n1p1`, `ro,nosuid,nodev,relatime`).
- Dataset: `/mnt/TestData/read_files/single_file_bench.bin`, 10 GiB (10,737,418,240 B).
- Workspace `/home/david/projects/JUring` is on a *different* disk (WD SN850, btrfs,
  `compress=zstd:1`); it was used only for JSON/TSV artifacts, **never** for I/O numbers.
- All I/O is O_DIRECT; every run used `--readonly` / read-only open. **No write path was
  measured** (impossible: the data mount is read-only in this sandbox).

## 2. Protocol

**fio (phase 1).** 3 reps per case, `--time_based --runtime=10 --ramp_time=2`,
`--direct=1 --readonly`, JSON per rep, `taskset -c 2` for single-job runs; `numjobs=2/4/8`
pinned to CPUs `2-3`, `2-5`, `2-9`. Exact command lines, per-rep loadavg and a check that
no other fio was running are in [fio-runlog.txt](../bench/results/2026-11-13/fio-runlog.txt).
Flagged cases were re-run once and both passes are reported (see §5); no rep was discarded.

**JUring (phase 2).** For every rep: separate JVM + separate ring + separate fd
(`--runs 1` per invocation), 10 s measured + 2 s warmup, `--readonly --threads 1`,
fixed `--seed 20261113`, `taskset -c 2`, JSON per rep into `bench/results/2026-11-13/juring/`.
Mean ± stdev is across the 3 reps. Per-rep loadavg, global CPU busy and `nvme1n1` read-sector
deltas are in [juring-external.tsv](../bench/results/2026-11-13/juring/juring-external.tsv).
The harness is `bench/juring/JUringFileBench.java` (build/CLI manifest in §8).

**Why a separate process per JUring rep:** it matches the fio protocol (one fresh ring/fd
per rep) so the comparison is like-for-like; each rep pays JVM startup + a 2 s warmup before
the measured window.

**Latency caveat:** the JUring harness timestamps from just before request preparation to
completion, so its "latency" includes submission-side work; fio's `clat` does not.
**IOPS/MiB/s are directly comparable; latency figures are not.**

Machine state was clean during phase 2: loadavg stayed ≤ 1.2 (mostly 0.3–0.8),
global CPU busy during reps 1.0–5.5 %, `nvme1n1` idle outside reps, no fio/java
benchmark observed running concurrently. Phase 1 had loadavg up to ~4, partly from our own
`numjobs=8` fio processes and io_uring workers (see §5).

Observations (fio only):

- io_uring and libaio are identical up to QD16; at QD64/128 io_uring is ~7–8 % faster and

## 5. JUring vs fio (same protocol, same file, 3 reps each)

Δ = (JUring − fio) / fio. A verdict of "not distinguishable" means the 95 % CIs overlap.

| pair | JUring IOPS (mean±sd, n) | fio IOPS (mean±sd, n) | Δ | 95% CIs overlap? | verdict |
|---|---|---|---|---|---|
| rr4k_qd1 vs fio io_uring QD1 | 11,081 ± 42 (n=3) | 10,901 ± 180 (n=3) | +1.7% | yes | not distinguishable |
| rr4k_qd16 vs fio io_uring QD16 | 143,714 ± 259 (n=3) | 143,332 ± 2,355 (n=3) | +0.3% | yes | not distinguishable |
| rr4k_qd64 vs fio io_uring QD64 | 324,186 ± 679 (n=3) | 297,931 ± 2,256 (n=3) | **+8.8%** | no | JUring faster |
| rr4k_qd128 vs fio io_uring QD128 | 420,794 ± 188 (n=3) | 303,258 ± 2,026 (n=3) | **+38.8%** | no | JUring faster |
| sq1m_qd1 vs fio io_uring 1M QD1 | 1,791 ± 3 (n=3) | 1,658 ± 35 (n=3) | **+8.0%** | no | JUring faster |
| sq1m_qd8 vs fio io_uring 1M QD8 | 4,769 ± 2 (n=3) | 4,697 ± 81 (n=3) | +1.5% | yes | not distinguishable |
| sq1m_qd32 vs fio io_uring 1M QD32 | 4,775 ± 0 (n=3) | 4,774 ± 2 (n=3) | +0.0% | yes | not distinguishable |

Reading of the deltas:

- At QD1/QD16 both stacks are bounded by the drive; the engines are equivalent.
- At QD64 JUring sustains **+8.8 %** IOPS; at QD128 the gap widens to **+38.8 %** because
  fio's io_uring is flat from QD64→QD128 (298k→303k) while the JUring harness scales
  324k→421k. That gap is repeatable across the 3 reps (CV 0.0–0.2 %) but **not yet
  explained**: it may be fio's own submission/completion bookkeeping rather than an
  intrinsic io_uring property. Do not use it as a seastar proxy.
- 1M seqread: only QD1 differs (+8.0 %); QD8/QD32 are bandwidth-bound at ~4.77 GiB/s and
  identical.
- These comparisons use different random offset streams (JUring xorshift with a fixed seed;
  fio `randrepeat=1` + its random map) and different latency definitions; throughput deltas
  are the robust part.

## 6. Bimodal performance state (important for M1/M3)

At 4K/io_uring the host showed **two distinct performance states**, not ordinary noise:

| observation | fast state | slow state |
|---|---|---|
| JUring QD64 randread | 323,405 / 324,516 / 324,636 IOPS (matrix) and 325,116 / 324,254 / 280,535 in diagnostics | 257,732 (first 3 s smoke), 254,849 (10 s diagnostic) |
| fio io_uring QD64 | 297,048 / 296,348 (reps 2–3) | 254,913 (rep 1) |
| p99 (JUring, QD64) | ~490 µs | ~1,764–2,075 µs |
| p999 (JUring, QD64) | ~993 µs | 4,698–5,896 µs |
| max (JUring, QD64) | 4.4–6.1 ms | 9.5–10.0 ms |

Evidence it is not a harness bug or GC:

- all JSONs report exact op accounting, `errors=0`, no `seqOverflows` anomaly at 4K;
  `nop` control is stable at ~7.4 M ops/s (0.8 % CV);
- a 10 s run with `-Xlog:gc` showed GC pauses only during JVM startup and after the measured
  window, none inside it;
- CPU stayed at 4.2–4.5 GHz in both states; loadavg was 0.3–1.2; between-run `nvme1n1`
  activity was 0 sectors; no concurrent fio/java benchmark was observed;
- the slow state appeared in **both** fio and JUring, and a re-run immediately after switched
  back to the fast state with identical flags.

Interpretation: machine/device-internal state (power/thermal/GC-of-SSD or brief external
interference we cannot see from inside the sandbox), with a ~25 % throughput swing and a
4× p99 swing. **Any 5 % engine delta can be swamped by a single run in the wrong state.**
M1/M3 must classify or gate this state, e.g.: run one throw-away warm-up rep and only accept
runs whose p99 is < ~600 µs at QD64, or repeat until three consecutive reps agree, and always
record the state alongside the number. The confirmation-run protocol used here (re-run
flagged cases once, report every raw JSON) is the minimum acceptable bar.

## 7. What this does and does not tell us

**Does tell us**

- Current read-path envelope of this host/device: 4K randread ~324k IOPS (JUring, QD64),
  ~421k (JUring, QD128), ~298–303k (fio io_uring QD64/128); 1 MiB seqread ~4.78 GiB/s.
- A like-for-like JUring-vs-fio comparison: JUring's JVM/FFM harness matches fio at low QD,
  and beats it by 8.8 % at QD64 and 38.8 % at QD128 (with the caveat above).
- fio engine/config guidance: libaio ≈ io_uring ≤ QD16, io_uring better at high QD; default
  batching beats `iodepth_batch_submit=8/16`; multiple rings help only up to ~4.
- The measurement floor: `nop` at 7.4 M ops/s rules out harness overhead as the explanation
  for the QD128 gap or for the state changes.

**Does not tell us**

- **No seastar numbers.** seastar cannot be run in this sandbox; a seastar-vs-JUring
  comparison still has to be produced on a machine where seastar's reactor works.
- **No write path** (data mount is read-only here).
- Nothing about the seastar shard model (one reactor per core, registered files,
  cross-shard submission) or multi-threaded JUring; this is single-threaded, single ring.
- Nothing about SLC/DRAM cache state or the drive's thermal history — and §6 shows that
  state matters. "SLC/thermal state unknown" applies to every row above.
- JVM warmup/GC effects are bounded by the 2 s warmup and the separate-process protocol, but
  the comparison still measures a JVM-based harness vs a C program; the JVM's own overhead is
  in the JUring numbers (it is not a pure-JUring-library microbenchmark).
- The sandbox's other tenants are invisible (`/proc` is namespaced); loadavg and CPU busy were
  recorded per rep but cannot prove the absence of external interference.
- Single consumer drive (Phison E16, 1 TB) with `max_sectors_kb=128`; results may not
  transfer to datacenter NVMe or to the target hardware in the plan.
- The QD128 difference between fio and JUring is unexplained; it is a fact about these two
  programs on this host, not a law about io_uring or seastar.

## 9. seastar L0 addendum — in-sandbox build, 2026-11-13 (same day)

The seastar checkout was moved into the repo at `SeaStarRef/` and built **inside this
sandbox without root** (local dependency sysroot, see `bench/seastar/build-and-run.md`).
This makes a real three-way L0 comparison possible on the *same* 10 GiB file, same

### 9.1 Build / run configuration

- `SeaStarRef/` @ `04b1c04d` (`seastar-25.05.0-1392-g04b1c04d`), release
  (`RelWithDebInfo -O3`), `io_uring` reactor backend (the default when the probe
  succeeds; confirmed in the log: `Reactor backend: io_uring`), GCC 16.1.1.
- Sandbox build against Fedora 44 `-devel` rpms extracted into `.sysroot/`; CMake
  3.31.6 / Ninja 1.12.1 in `.tools/`. A host build with `sudo ./install-dependencies.sh`
  is still the supported path; this one lacks GnuTLS/LTTng/tests and uses OpenSSL.
- Runtime flags per cell: `--smp 1 --cpuset 2 --memory 1G --lock-memory 0`, `taskset -c 2`.
  No hugetlbfs exists in the sandbox → THP path; this is the best configuration
  available here (F0: best config, disclosed).
- Runner: `bench/seastar/seastar_file_bench` (new, `bench/seastar/seastar_file_bench.cc`)
  opens `/mnt/TestData/read_files/single_file_bench.bin` **read-only** and issues
  `file::dma_read` / `dma_write` from `--qd` fibers; 4 KiB-aligned unregistered buffers

  It emits the same JSON schema as `JUringFileBench`.
- seastar engine differences (not hidden): stock 200-entry io_uring, **no**

  io_queue + futures in the path.

### 9.3 Reading

- **The engines are close across the board: within ±5% at every QD.** seastar is ahead
  at low QD (QD1/QD16, where per-op latency/overhead dominates), JUring is ahead at high
  QD (QD64/QD128, where batching + fixed buffers/DEFER_TASKRUN pay off). Neither side is
  "30× faster"; a single-number headline would be dishonest in either direction.
- **fio is a bad proxy for seastar at high QD.** fio's default io_uring submission
  (batch=1, no registration) measured 297.9k @QD64 / 303.3k @QD128, while seastar reached
  319.5k / ~399k. The JUring-vs-fio numbers in §5 understate seastar; the fair comparison
  is the table above (and M1 adds matched fio + `io_tester` cross-check).
- Both engines hit the same device ceiling: 1M seqread ~4.77 GiB/s and 4K ~469k IOPS
  with 4+ jobs. Headroom is in CPU cost/op and tails, not raw IOPS.
- Caveats: one build, one machine, 3 reps, no hugepages, no io_tester cross-check, QD128
  slow-state variance, and seastar's numbers include its default configuration rather
  than a tuned one. M1 is where these get tightened.
