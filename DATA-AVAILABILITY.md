# Benchmark data availability

JUring's published performance claims are backed by raw per-repetition artifacts and analysis
scripts. The repository does not commit the raw run directories (they are large, host-specific
and regenerated by the harness), but every claim in [BENCHMARK.md](BENCHMARK.md) names the report
and campaign that produced it, and the harness under [`bench/`](bench/README.md) can reproduce
the analysis from raw data.

## What is committed

- `bench/` — the runnable harness: run scripts, analyzers, fio/Seastar/JUring drivers, the
  measurement contract ([docs/benchmark-methodology.md](docs/benchmark-methodology.md)), and the
  quick-start instructions in [bench/README.md](bench/README.md).
- `BENCHMARK.md` — the published tables, with the report section and raw-artifact path for each
  claim.
- `docs/benchmark-methodology.md` — the pre-registered measurement protocol, acceptance rules,
  device-state gating, statistics and threats to validity.
- The internal campaign reports (`docs/internal/m1-report.md`, `docs/internal/m1-write-report.md`,
  `docs/internal/m2-report.md`, `docs/internal/m3-report.md`, `docs/internal/stepd-report.md`, `docs/internal/b6-report.md`) — the authoritative
  per-campaign analysis.

## What is not committed

- `bench/results/` (gitignored): per-rep JSON, manifests, cell-meta ledgers, device series and
  aggregate JSON produced by a campaign. These are host- and device-state-specific.
- `nvme-data/`, `scratch/`, `SeaStarRef/` (gitignored): local data file, session notes, and the
  Seastar reference checkout used as a benchmark comparator.

## Release data archive

Each release publishes a checksummed tarball attached to the GitHub release containing the
aggregate JSON, manifests and analyzer outputs behind the release's claims, plus the SHA-256 of
the analyzer scripts used to produce them. The archive is a snapshot of the campaigns cited in
[BENCHMARK.md](BENCHMARK.md); it is not a merged raw dataset across hosts.

Reproduction path:

```sh
# Full protocol and prerequisites:
sed -n '1,120p' docs/benchmark-methodology.md
# Re-generate aggregates from a raw session directory (no device I/O):
python3 bench/m1/analyze_m1.py --dir bench/results/<session> [--out-prefix ...]
# One-command comparison quick start (writes under bench/results/):
./bench/run-comparison.sh
```

## Caveats to carry when citing these numbers

- The headline campaigns ran on **one host and one consumer NVMe** (AMD Ryzen 9 3950X, GIGABYTE
  GP-ASM2NE6100TTTD 1 TB, ext4, Fedora 44, kernel 7.0.12). Absolute IOPS are device-state
  dependent; see the device-state gating sections in the reports and `BENCHMARK.md`.
- The write path is published as **INCONCLUSIVE** (`docs/internal/m1-write-report.md`): the
  consumer NVMe exhibits SLC-burst/TLC-folding cliffs, so no write-parity ranking is claimed.
- fio reference cells are registration-matched; the read-path reference uses fio's default submit
  batching (see the fio configuration notes in `BENCHMARK.md`). Seastar is reported as a bracket
  with an explicit asymmetry section, not as an equal-config opponent.
- Benchmark data is evidence for the claims in this repository, not a portable performance
  guarantee for other hardware, kernels or filesystems.

## Verifying a claim

Every BENCHMARK.md row names its report section; the report tables are generated from aggregate
JSON by the analyzer, and the aggregate JSON is rebuilt from the raw per-rep files. The release
archive contains the aggregate JSON and manifest needed to re-run the analyzer and reproduce the
published tables to rounding. If a claim is ambiguous or lacks its artifact path, treat it as a
documentation bug and report it.
